Importpfade auf `custom_components.gmx_mail_mcp` umgestellt, Tests laufen unter Python 3.14 ohne HA-Plugin. |
| D6 | 2026-11-23 | Übernommene Entscheidungen der Vorlage gelten weiter, außer „kein eigener MCP-Server“ (Vorlage Nr. 1) und die ha-mcp-Freigabe (Nr. 9): Nr. 3, 6, 10, 19–24, 36, 40 (Details in `gbasedow/gmx_mail`, `docs/DECISIONS.md`). | Gleiche GMX-Eigenheiten, gleiche Sicherheitsüberlegungen. |
| D7 | 2026-11-23 | `gmx_mail` wird nach erfolgreichem Betrieb von `gmx_mail_mcp` **abgelöst**. | D8 | 2026-11-23 | Autorisierung wie beim eingebetteten ha-mcp: Long-Lived Access Token von Home Assistant genügt (Bearer). Kein eigenes OAuth. | D9 | 2026-11-23 | Zugriff nur für **einen eigenen HA-Benutzer**: Der Nutzer erzeugt die Tokens unter diesem Benutzer. Der Endpunkt lehnt Tokens anderer Benutzer ab (Option „erlaubter Benutzer“, wird im Config-Flow gewählt). | Vorgabe des Nutzers. Zweite Sperre neben dem Token; ein Token eines anderen Benutzers öffnet den Server nicht. |
| D10 | 2026-11-23 | Anhänge sind **als Text und als Datei** abrufbar: `get_attachment` mit Parameter `mode` = `text` / `file` / `both`. Textextraktion für PDF, DOCX, XLSX und reine Textformate; die Datei kommt als MCP-Inhalt (Bild/Blob). | Vorgabe des Nutzers. Offen bleiben Größenlimit, Teilabruf und die Auswahl reiner Python-Bibliotheken für die Extraktion (Kompatibilität mit HA, kein kompiliertes Paket). |
| D11 | 2026-11-23 | **Mehrere GMX-Konten** werden unterstützt: ein Config-Entry und ein Endpunkt je Konto (`/api/gmx_mail_mcp/<entry_id>/mcp`). | Wunsch des Nutzers. |
| D12 | 2026-11-23 | Tool-Schalter nur im **Konfigurationsfluss** (Options-Flow), nicht als HA-Entitäten. Voreinstellung: nur lesende Tools (Stufe R) an. | Vorgabe des Nutzers. Als Entitäten könnte ein LLM mit ha-mcp-Zugriff sich Tools selbst freischalten. |
| D13 | 2026-11-23 | Umfang: Postfach **vollumfänglich verwalten**. Zusätzlich zu den 21 Aktionen der Vorlage: Roh-Mail (.eml), Threads, Ordner abonnieren, `.eml` hochladen, Capabilities, Keywords. Mailbox-weites `EXPUNGE` bleibt ausgeschlossen (nur `UID EXPUNGE`). | Vorgabe des Nutzers; der Ausschluss ist eine Sicherheitsgrenze aus der Vorlage und ändert nichts an der Verwaltbarkeit. |
| D14 | 2026-11-23 | Größenlimit für Anhänge **konfigurierbar**, Voreinstellung **10 MB**. | Vorgabe des Nutzers. |
| D15 | 2026-11-23 | Keine Sensoren und keine Ereignisse in der ersten Version; damit keine dauerhafte IDLE-Verbindung. | Nutzer braucht sie nicht. Spart eine der höchstens zwei GMX-Verbindungen und vermeidet Dauerlast; kann später als Option nachgerüstet werden. |
| D16 | 2026-11-23 | Python 3.14 wird vorausgesetzt (HA 2026.11). Die Version der echten Instanz wird vor M1 am laufenden Container bzw. in den Systeminformationen bestätigt. **Bestätigt 24.11.2026: 2026.11.3.** | Aussage des Nutzers; die Vorlage nennt ≥ 3.14.2 aus Recherche, ungeprüft. |
| D17 | 2026-11-23 | Anhänge beim **Senden** kommen direkt im Tool-Aufruf (base64 im Argument `attachments[]` mit Name, Typ, Inhalt). Prüfsumme (SHA-256) im Argument, damit beschädigte Dateien auffallen. |
| D18 | 2026-11-23 | Das Repository bleibt bewusst **öffentlich** (MIT). | Entscheidung des Nutzers. Keine Zugangsdaten im Repo; Prüfung vor jedem Commit. |

| D20 | 2026-11-24 | **Eigene schlanke JSON-RPC-Schicht** für MCP (Streamable HTTP, nur `POST`, zustandslos; Methoden `initialize`, `ping`, `tools/list`, `tools/call`, Benachrichtigungen), kein `mcp`-SDK. Nur aiohttp aus HA, keine neue Abhängigkeit. | Wahl des Nutzers (OFFENE-PUNKTE Nr. 7). Geprüft am 24.11.2026: HA-Core `mcp_server` (2026.11.3) pinnt `mcp==2.3.0`, `anyio==4.15.1`, `aiohttp_sse`; das SDK zieht Starlette, uvicorn, pydantic, jsonschema, opentelemetry nach, sein HTTP-Transport passt nicht zu aiohttp-Views, und ein eigener Pin hinge an jedem HA-Update. Protokollkonformität wird mit Tests gegen die MCP-Spezifikation und mit einem echten Client (Claude Code) abgesichert. |
| D21 | 2026-11-24 | Formular-Schemas mit **`probatio`** statt `voluptuous`. | Technischer Befund in M0: HA 2026.11.3 hängt nur noch von `probatio` ab, die Formular-API (`async_show_form`) ist auf `probatio.Schema` typisiert; `voluptuous` ist nur noch indirekt (über `annotatedyaml`, `hass-nabucasa`) installiert. |
| D22 | 2026-11-24 | Zugriff wie ha-mcp im Modus `ha_auth`: Die Integration **zeigt die Verbindungs-URL** an (Konfigurieren-Bildschirm, externe bzw. Nabu-Casa-URL). **Claude Code** und andere Clients mit Header melden sich mit einem Long-Lived Access Token (Bearer) an; **claude.ai** über OAuth mit **Home Assistant als Anmeldestelle** (HA-Login-Seite, Benutzer = gewählter MCP-Benutzer, D9). Kein eigener OAuth-Server, keine geheime URL, keine Seite zum Einfügen eines Tokens. Präzisiert D8. | Wunsch des Nutzers („wie ha-mcp“). Geprüft am 24.11.2026 im Quellcode von ha-mcp (`custom_components/ha_mcp_tools`, `docs/in-process-server.md`): ha-mcp lässt in claude.ai kein Token einfügen, sondern nutzt HA-Login (`ha_auth`), geheime URL (`none`) oder Client-ID/Secret (`legacy`); ein eingefügtes Token gibt es nur in der separaten OAuth-Beta (Docker). HA 2026.11 beantwortet 401 an `requires_auth`-Views mit `WWW-Authenticate: Bearer resource_metadata=…` und liefert `/.well-known/oauth-protected-resource` und `/.well-known/oauth-authorization-server` (mit Client-ID-Metadata-Document) selbst aus – für unseren Endpunkt per Test bestätigt. Live-Test 24.11.2026: Connector aus claude.ai verbindet sich und ruft Tools auf (docs/M1.md). |
| D23 | 2026-11-24 | Die **Einzelschalter je Tool** (`enabled_tools`) ersetzen die Stufen-Berechtigungen der Vorlage (`permissions`) als Schaltmechanismus. Die Stufe R/O/D/S bleibt Eigenschaft jedes Tools: Sie bestimmt die Voreinstellung (nur R an) und die MCP-Annotationen (`readOnlyHint`, `destructiveHint`). Ohne gespeicherte Auswahl gilt die Voreinstellung; nach dem ersten Speichern ist die Liste **explizit**: Tools, die ein späteres Update hinzufügt, bleiben aus, bis sie eingeschaltet werden – auch lesende. Optionen der Vorlage (Versandmodus, Allowlist, Limits, Ordner) erscheinen im Options-Flow erst in dem Meilenstein, in dem sie wirken. | Zwei Schalter-Mechanismen nebeneinander wären verwirrend; die Vorgabe des Nutzers ist „jedes Tool einzeln“ (D12). Explizite Liste: kein Update schaltet unbemerkt Zugriff frei. |
| D24 | 2026-11-24 | `aioimaplib` aus den Laufzeit-Abhängigkeiten im Manifest entfernt, `iot_class` = `cloud_polling`. `client/idle.py` bleibt samt Tests im Repo (für eine spätere Option). | Ohne IDLE (D15) importiert kein Laufzeitpfad `aioimaplib`; weniger Pakete in HA. Abrufe geschehen nur auf Anfrage. |
| D25 | 2026-11-24 | Der Endpunkt prüft das Bearer-Token **selbst mit HAs eigener Prüfung** (`hass.auth.async_validate_access_token`, `async_user_not_allowed_do_auth`) statt über `requires_auth` (`auth.py`). 401 ohne Token und 401 mit echtem, nur **abgelaufenem** HA-Token zählen **nicht** für die IP-Sperre; jede andere fehlgeschlagene Anmeldung (falsches Schema, gefälschtes, widerrufenes Token, inaktiver Benutzer, Nur-lokal-Benutzer von außen) zählt wie bisher (`process_wrong_login`). Gesperrte IPs blockt weiterhin HAs Middleware; Tokens nur aus dem Header. Ändert D2 (dort `requires_auth`). | Nutzerinstanz hat `login_attempts_threshold: 5`, der Nutzer will ihn nicht dauerhaft erhöhen. Mit `requires_auth` zählt HA jede 401 – auch die OAuth-Anmeldeaufforderung des Connectors und abgelaufene 30-min-Tokens; eine Sperre träfe alle Anfragen dieser IP, also auch ha-mcp. Geprüft in Tests (echte Sperre mit Schwelle 3, Gegenprobe mit 6 eingebauten Fehlern) und gegen ein frisches HA 2026.11.3. |
